# Agents 一览与使用说明

> 程序都在 `backend/app/`：`agents.py`（agent 逻辑）、`freshness.py`（保鲜度）、`llm.py`（调用 LLM）、`main.py`（API 入口）。提示词只有一份来源：[07_提示詞](07_提示詞.md)。API 格式见 [09_接口文档](09_接口文档.md)。
> 原则：**程序做得到的用程序**（分群、统计、引用核验、条件比对、数红绿灯、算日期），LLM 只做判断与审查。

## 整体流程

〔 〕＝agent，编号对应下面总表。

```
分享者发文 →〔#1 抽决策点〕→ 数据库 ←〔#9 通知抽规则〕← 爬光华官网通知
                │                         ↓
                └→〔#8 抽主张〕→〔#10 判断还成不成立〕→ 文章页标 🟢🔴🟡
                                ↓
读者搜索 →〔#2 听懂问题〕→ 找人＋分群 →〔#3 每群挑代表〕→〔#4 审查〕→ 搜索结果
              │                                         ＋〔#11 每篇推荐理由＋红绿灯〕
              └→ 主题／热门／人物页「AI 帮我选」→ 筛选 ＋〔#11〕
                                ↓
                             搜不到
                                ↓
                        我想看（满 5 人）→〔#6 找分享者来写〕→ 回到「分享者发文」

分享者设可约时间／读者说哪时有空 →〔#7 日历助手〕→ 程序算日期
```

## 白话：每个 agent 在做什么

以搜索「双非计算机大三，要不要考研」为例：

1. **决策点抽取：把文章变成可以搜索的数据**。分享者发文时，读全文找出作者「做决定」的时刻（例：保研名额不够 → 决定考研 → 考上北大软微），每个时刻填成 11 个字段（学校层级、专业、考虑过哪些选项、最后选了什么、结果、原话⋯）。写作页按「发布」会先显示抽出来的结果让作者改，确认后才真的发。之后搜索和比对都靠这些字段。
2. **处境抽取：听懂读者在问什么**。把那句话先改错字（光滑→光华管理学院），再拆成条件：学校层级＝双非、专业＝计算机、年级＝大三、决策类型＝考研。LLM 出错才退回关键词比对。
3. **判断 agent：从每一群里挑最像你的人**。搜索结果先用程序分好群（例：考研成功／考研失败／起点比你好），每一群派一个判断 agent 同时跑，挑最多 2 位代表，写出为什么像你、跟你的差别、引用的原话。拿不准时会去查那个人的其他文章看前后经历，每群最多查 4 次。整群都不像读者就把这群拿掉。
4. **审查 agent：检查判断 agent 有没有乱讲**。看理由有没有根据、差别有没有讲错、是不是硬凑；不通过就附上意见退回重判，最多退 2 次。通过的群，画面上标「✓ 已审查」。
5. **退路说明：还没接**。原本设计是 agent 超时时，改用一次 LLM 帮前 5 人各写一句参考价值；现在超时是直接只显示排序结果，没有说明。
6. **邀请分享者：搜不到时找人来写**。读者按「我想看」满 5 人时要找 5 位分享者：先用程序比对条件；像「医学部转金融」这种条件对不上任何人的需求，才交给 agent 看每位分享者的头衔和文章标题，判断谁最可能写得出来。
7. **日历助手：一句话设可约时间**。分享者打「下周一到五晚上 8 点到 11 点都可以，周三除外」，agent 只把话变成规则（哪几天、星期几、几点），日期由程序算（LLM 容易算错「下周三是几号」）。没说几点就反问，不会自己开满 24 小时。结果先在月历上预览，按「确认保存」才存。读者那边打「我下周末下午有空」，程序拿展开结果跟分享者还能约的时段取交集，用 ★ 标出来。
8. **保鲜度：主张抽取**。文章提到光华时，找出讲「招生规则」的句子（例：「第三批可以交前 6 学期成绩单」），心得、准备方法这类主观经验不抽。
9. **保鲜度：通知抽规则**。每天爬光华官网的夏令营通知，新通知才把它整理成 8 类规则（申请时间与批量、开营时间、申请资格⋯）。
10. **保鲜度：判断**。拿最新一年的规则，逐句判断文章里的主张现在还成不成立：🟢 仍成立、🔴 已改变（附「现在变成什么样」和官方原文）、🟡 待更新（依据的通知是去年的，今年的还没出）。
11. **列表推荐理由（红绿灯）**。搜索页、主题／热门／人物页的「AI 帮我选」找出文章后，每篇写「为什么推荐给你」「这篇独有的点」「原话」，再把读者的话拆成几个条件、每篇回报对上哪几条，**程序**照比例数成红绿灯：全对＝红（很匹配）、至少三分之二＝黄、其余＝绿（可能会想看）。

另外几步是纯程序、不是 agent：**分群**、**引用核验**（所有 agent 引用的原话在原文找不到就删掉）、**主张挂规则**、**数红绿灯**、**展开日期**。

## 二、各 agent 说明

### 1. 决策点抽取（流程 A）

- **触发**：`POST /api/articles/extract`（写作页预览，给作者改）；`POST /api/articles`、`PUT /api/articles/{id}` 没带 `decisionPoints` 时；开发用 `POST /api/articles/{id}/extract`（`DEV_EXTRACT=1` 才开）
- **输入**：标题＋全文（图片行先拿掉）＋作者背景
- **输出**：多个决策点，每个 11 栏＋各栏 confidence
- **防呆**：pydantic 验格式，错了带错误重问一次；`原话` 必须逐字出现在全文，查不到改「未提及」；作者确认过的决策点后端照样校验
- **退路**：没 key／出错 → 存「未提及」占位，文章照样发布；决策类型是「未提及」时保留原分类

### 2. 处境抽取（流程 B ①）

- **触发**：搜索时看 `.env` 的 `SEARCH_LLM_PARSE`（本机与在线都是 `1`）；「AI 帮我选」（`/api/filters/parse`）一律用 LLM
- **输入**：读者打的那句话（繁体先转简体）
- **输出**：筛选条件（决策类型、学校层级、专业⋯）＋读者处境＋改正错字后的检索句＋是否无关问题
- **防呆**：枚举字段只收合法值（例：学校层级只收 985／211／双非）；专业名对齐库里写法；`temperature=0`，同一句每次抽得一样
- **退路**：出错 → 关键词版（规则在 `website/frontend/src/data/searchRules.json`，前后端共用）
- **缓存**：「AI 帮我选」的抽取结果按句子缓存；关键词退路的不缓存

### 3. 判断 agent（流程 B ⑤）

- **触发**：搜索结果分群后（④），每群开一个线程同时跑
- **输入**：读者处境、搜索字、这群前 8 人的决策点
- **工具**：`get_person_timeline(person_id)` 看某人所有文章的决策点；**每群最多 4 次**，到上限就要求直接给结论
- **输出**：整群像不像（不像 → 前端拿掉这群）；最多 2 位代表，各附「为什么像你」「跟你的差别」「引用原话」
- **防呆（⑥ 引用核验，纯程序）**：代表必须在这群里、最多 2 人；原文查不到的引用直接删
- 做完一群马上推给前端（SSE `group` 事件），不等其他群

### 4. 审查 agent（流程 B ⑦）

- **输入**：读者处境、判断 agent 的结论、被选代表的决策点
- **输出**：通过／不通过＋问题清单
- **不通过**：带审查意见叫判断 agent 重判，**最多打回 2 轮**；第 2 轮还不过 → 只留没被点名的代表
- 通过 → 前端该群标「✓ 已审查」（SSE `review` 事件）

**整段时限**：搜索 agent 层（⑤–⑦）超过 `AGENT_TIMEOUT` 秒，没做完的群维持关键词版。全部审完的结果缓存 `SEARCH_CACHE_TTL` 秒，同样的搜索直接重播；发文／改文／删文时清掉。

### 5. 退路说明（未接）

07 #5 的提示词写好了但程序没用：现在超时就是留关键词版，不另外叫 LLM 补一句说明。要接的话放在 `run_search` 的超时分支。

### 6. 邀请分享者（求经验 ③）

- **触发**：`POST /api/wishes`，按「我想看」的人数**刚好到 5**（`WISH_NOTIFY_AT`）那一下，只发一次；同一人按几次都只算一次
- **怎么挑**：
  1. 规则：比对读者勾的条件（决策类型、学校层级、专业、结果、年级、年份），对上越多越前，同分看推荐数，取前 5
  2. **一个条件都对不上的人都没有**才交给 agent：给它所有分享者的头衔、一句话摘要、文章标题，挑 5 位
  3. agent 用不了 → 推荐数最高的 5 位
- **防呆**：agent 编造的 id、重复的都去掉
- **结果**：在 `notifications` 写 `invited` 通知，记在分享者名下（`person_id`），还没注册的人注册后登录就看得到
- **已知问题**：「医学转金融」漏选了林书瑶（临床起点），prompt 待调

### 7. 日历助手

- **触发**：`POST /api/me/availability/assist`（只回预览，不写库）
- **输入**：今天（北京时间）、正在看的月份、目前月历上的时段、分享者那句话
- **输出**：规则（add／remove、from／to 或 dates、weekdays、hours）＋一句理解（note）；听不懂或**没说几点**回 ask 问句（10/22 改：原本没说几点会开满 24 小时，提示词与程序两边都挡）
- **程序展开**（`expand_rules`）：只套到正在看的月份、跳过已过去的时段、不删已被约走的、坏的小时丢掉
- **确认**：前端预览差异，分享者按「确认保存」才走 `PUT /api/me/availability`
- **实测**（Flash，各约 2–4 秒）：「下周一到五晚上 8 点到 11 点都可以，周三除外」→ 12 个；「这个月周末全天，但 25 号不行」→ 96 个；「每天下午」→ 理解成 13–16 点；「周末可以」→ 只放这个周末（note 有写，预览看得到）
- **读者端**：`POST /api/persons/{pid}/slots/assist`（要登录），同一段 prompt 展开读者有空的时间 → 跟分享者还能约的时段取交集 → 预约弹窗用 ★ 标出、跳到第一天
- **读者端实测**（分享者开 24／25／28／31 号的 10、15、20 点）：「我下周末下午有空」→ 24、25 号 15 点 ✓；「月底那几天都行」→ 25 号以后 9 个 ✓；「我随时」→ 全部 12 个 ✓

### 8–10. 经验保鲜度（流程 D，只做光华）

文章里讲的招生规则可能已经过时，拿光华最新官方通知逐句核对。**主张挂规则、引用核验、🟡 待更新都是程序做，LLM 只抽和判。**

| | #8 主张抽取 | #9 通知抽规则 | #10 判断 |
|---|---|---|---|
| 触发 | 发文、改正文后背景线程跑（不拖慢发文；只改标题不重跑） | `python -m app.freshness crawl` 抓到新通知 | #8 抽完判这篇；新通知进来后重判受影响的规则 |
| 输入 | 标题＋正文 | 通知全文（PDF 先转文本）＋项目＋年份 | 一条最新规则＋通知全文＋底下所有主张 |
| 输出 | 句子＋项目（专硕／学术夏令营）＋规则类型 | 每类一条规则（内容＋关键原文） | 每句 valid／changed／unknown＋理由＋官方原文 |
| 防呆 | 句子逐字核对正文；项目、类型不在枚举就丢 | 原文逐字核对通知；同类多条合成一条 | 原文对不上最新通知 → unknown；没判到 → unknown |
| 退路 | LLM 出错保留旧标注，之后补跑 `index` | 列表页抓不到跳过那页 | 没有这类规则 → 全部 unknown |

- **省钱**：正文没有「光华」不叫 LLM；#10 一条规则一次判底下所有主张，成本跟规则数成正比、不跟文章数
- **显示**：`GET /api/articles/{id}` 带 `claims`；判「仍成立」但依据通知早于今年 → 读的时候算成 🟡 待更新
- **指令**（`backend` 目录）：`crawl` 抓新通知（设计是每天 cron 跑）／`index [aid ...]` 对文章抽主张并判断／`recheck` 全部重判（改 07 #10 后用）
- **官网连接**：http 稳定、https 偶尔握手失败；服务器连会被转 https，补了 RapidSSL 中继凭证（`rapidssl_g1.pem`，2027-11 到期）和旧加密套件

### 11. 列表推荐理由（红绿灯）

- **触发**：`GET /api/filters/why?q=`，搜索页和「AI 帮我选」都会叫；另一个请求，筛选／结果先出来、理由后到
- **输入**：读者处境、那句话、召回的文章（最多 30 篇＝RAG 召回上限）
- **做法**：
  1. 先单独叫一次只拆条件（不给文章、输出很短），之后几批共用同一份——各批自己拆会拆得不一样，同样的经历在不同批灯号不同
  2. 每 8 篇一批平行问，每篇回 why（20 字内）、unique、quotes、matched（对上哪几条条件）
  3. **程序数灯**（`match_level`）：全对 `high`（红）、至少三分之二 `mid`（黄）、其余 `low`（绿「可能会想看」）；模型只判断每条对不对得上，不让它数
- **防呆**：quotes 逐字核对原文、查不到删；编造的文章 id 丢掉
- **退路**：某批失败就少那批；全失败或没 key 回空，卡片不显示理由与灯
- **缓存**：按句子缓存；发文／改文／删文时清（`clear_caches()`）
- **搜索页排序**：灯到了以后群内按红→黄→绿→没灯稳定排序
- **已知**：同一句话红绿灯篇数每次可能不同；灯约晚搜索结果 7 秒到，试过合进搜索 stream 没变快、已撤回（10/22）

## 三、使用说明

### 设置（仓库根目录 `.env`）

| 变量 | 作用 | 现在 |
|---|---|---|
| `LLM_API_KEY` | 没填 → 所有 agent 走退路，网站照样能用 | DeepSeek |
| `LLM_BASE_URL`、`LLM_MODEL` | 换供应商／模型（OpenAI 兼容格式） | deepseek-flash |
| `LLM_THINKING` | 设 `disabled` 关掉思考。**deepseek-flash／v4-pro 缺省开思考**（实测慢 5–10 倍、输出 token 多 6–30 倍），一定要关 | disabled |
| `LLM_TIMEOUT` | 单次请求秒数 | 30 |
| `LLM_CONCURRENCY` | 同时最多几个请求；10/17 实测 DeepSeek 2→8 整次平均 12.3→9.9 秒、0 次 429 | 8 |
| `AGENT_TIMEOUT` | 搜索 agent 层整段时限（秒） | 45 |
| `SEARCH_CACHE_TTL` | 搜索缓存秒数 | 1800 |
| `SEARCH_LLM_PARSE` | 设 `1` 才用 LLM 做处境抽取（没设＝关键词版） | 1 |
| `SEARCH_PER_MIN`、`PARSE_PER_MIN` | 搜索、「AI 帮我选」／推荐理由每 IP 每分钟上限 | 20、10 |

改完 `.env` 要重开后端。**demo 要关 VPN**（开着每次多约 2 秒）。

### 改提示词

1. 改 `docs/07_提示詞.md` 里对应的 ``` 代码区块。程序按**顺序**读 11 个区块（`llm.py` 的名单：extract、situation、judge、review、fallback、invite、calendar、claims、rules、fresh_judge、list_why），**不要插新区块在中间**，新的加在最后并在名单补名字
2. `{query}` 这类大括号是程序要填的变量，名字别改
3. 重开后端生效；改了 07 #10 要跑 `python -m app.freshness recheck`
4. **部署时 `docs/07_提示詞.md` 和 `website/frontend/src/data/searchRules.json` 都要带**，后端启动就读，缺了会崩

## 四、模型选择：Flash vs Pro（10/17 实测）

同一批 4 题搜索＋邀请 agent＋2 篇决策点抽取，两个模型各跑一次，**都关思考**（`LLM_THINKING=disabled`）。价格用 DeepSeek 官方尖峰价（北京时间平日 9–12、14–18 点；其余时段半价）。

**踩坑**：`deepseek-flash`／`deepseek-v4-pro` **缺省开思考**。开着时 Pro 每次搜索都撞 45 秒时限、抽取逾时失败；Flash 输出 token 暴增 6–30 倍。原本的 `deepseek-chat` 就是 Flash 关思考。

| | Flash | Pro |
|---|---|---|
| 价格（¥／百万 tokens：缓存命中／未命中／输出） | 0.04／2／8 | 0.30／9／27 |
| 搜索 4 题 | 3.9–10.3 秒，¥0.003–0.012 | 9.0–14.6 秒，¥0.016–0.063 |
| 邀请 agent | 2.2 秒，¥0.001 | 3.7 秒，¥0.019 |
| 决策点抽取 2 篇 | 2.6–3.1 秒，¥0.003–0.005 | 4.0–4.1 秒，¥0.013 |

**品质差别**
1. **用工具**：Flash 4 题一次都没查时间线；Pro 每群查 1–2 次——Pro 才像真的 agent
2. **乱讲**：Flash 第一轮写「同样在考研与工作之间摇摆，处境几乎完全重合」，数据没有，被审查 agent 退回；Pro 这次没有
3. **挑得准**：「考公还是读研」Flash 挑了研二法学在律所／选调／国考之间选的人；Pro 挑选项里同时有考公和考研的人，较对题
4. **审查严度**：Pro 的审查把整个「起点比你好」群拿掉，但这群本来就是展示起点比读者好的人——是审查 prompt 的问题，待调
5. **抽取**：两边各有错。Flash 多抽一个重复决策点、选项多了原文没有的「保研」；Pro 漏了标题写着的「计算机」专业
6. **邀请 agent**：关思考后两边都把林书瑶排第一

**现况**：在线用 **Flash**（速度优先，推荐理由加上去后一次搜索要打约 9 次 LLM）。要换 Pro 只改 `.env` 的 `LLM_MODEL`，换之前先确认 DeepSeek 余额（10/22 晚只剩 ¥6.55）。

测试脚本：一次性的，没进 repo；要重测照这段的设置再写一次即可。
