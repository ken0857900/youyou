## 二、流程 A：分享者写作 → 入库

```
输入 xxx@pku.edu.cn → 收验证码 → 验证通过（升级成分享者）
   ↓
自由写作（标题＋文章；提示文本鼓励写当时的你／考虑过的路／怎么选／结果，没走成的也写）
   ↓
按「发布」→ DeepSeek 抽出决策点 11 个字段（带入作者自填的本科层级／专业）→ pydantic 检查格式（文章没写的填「未提及」）
   ↓
作者在弹窗确认／修改决策点 → 确认发布
   ↓
切块（一个决策点一块）→ bge-m3 转成矢量
   ↓
同一个交易写入：文章 ＋ 决策点 ＋ 切块 ＋ 矢量 → 发布
   ↓
背景线程：保鲜度抽主张＋判断（流程 D，正文含「光华」才做）；清掉搜索与推荐理由缓存
```

先把矢量都算好再一次写进数据库：API 中途失败，数据库不会留下写到一半的数据。改文同样重建索引；删文时决策点、切块、交互一起删（外键 CASCADE）。

## 三、流程 B：读者检索 → 搜索结果（2026/10/16 改成 multi-agent）

**原则：程序做得到的都用程序做，agent 只负责程序做不到的判断。**
过滤、召回、排序、分群、算人数、核验引用都是程序；agent 只做「读文章判断处境像不像」和「检查判断站不站得住」。

```
读者输入搜索字（例：双非计算机 GPA3.4 大三，保研还是考研）
   ↓
① 处境抽取（DeepSeek，改错字＋抽条件）→ 自动勾好筛选条件（读者可再勾选或取消，没有必填）
   无关问题／注入 → 只显示分类入口
   ↓
② 两路召回，两路都先用 SQL 依勾选条件过滤
   ├ pgvector 矢量比对（意思相近）
   └ zhparser 全文检索（校名、科系这类关键字）
   → 合并约 30 笔
   ↓
③ bge-reranker 重排
   ↓
够相近吗？ ──否──→ 找不到结果页：拿掉条件建议／最接近的经验＋差别／分类入口／我想看
   │是
   ↓
④ 分群（程序）：照处境字段分（学校层级、专业、成绩区间、年级）
   各群统计（程序）：走了哪些路、成功／失败／转向人数
   ↓ 平行
⑤ 判断 agent × N（每群一个，DeepSeek）
   ・读文章判断字段看不出的处境差异
     （例：同是双非计算机，一个家里要他早点工作、一个想冲名校）
   ・挑代表人物，写「为什么是他／跟你差在哪」，每句附出处
   ・信息不够 → 调用 get_person_timeline 看那人前后的决策点
   ・整群都不像读者 → 标记，该群不显示
   ↓
⑥ 引用核验（程序）：原文查不到 → 删掉那句
   ↓
⑦ 审查 agent：理由站不住（例：说他是双非、其实是 985）→ 打回该群重判，最多 2 轮
   ↓
⑧ 模板组出结果：各群统计＋代表人物＋原话
   ↓
搜索结果页 → 人物页 → 预约／QR 名片

另一个请求同时跑（/api/filters/why，07 #11）：
   先拆读者条件一次 → 召回的文章（最多 30 篇）每 8 篇一批平行写推荐理由、回报对上哪几条
   → 程序核验原话、数红绿灯 → 结果到了群内按红→黄→绿排
   → 灯全绿＝库里没有答案 → 显示没有答案的画面＋「猜你想看」
```

实际传输：`/api/search/stream` 用 SSE，①–④（处境抽取、召回重排、分群）做完先推 `result`，还没经过判断 agent，之后每群判断完推 `group`、审查完推 `review`，最后 `done`；同一句话的 agent 结果缓存 30 分钟，发文／改文／删文时清。

### 哪一步给程序、哪一步给 agent

| 步骤              | 谁做                 | 为什么                                                         |
| ----------------- | -------------------- | -------------------------------------------------------------- |
| ② 过滤、召回     | 程序                 | SQL 和索引做得又快又稳                                         |
| ③ 重排           | 模型（bge-reranker） | 文本相近度，专用模型比 LLM 便宜                                |
| ④ 分群、算人数   | 程序                 | LLM 数数会错                                                   |
| ⑤ 判断处境像不像 | **判断 agent** | 字段表达不出的差异要读文章才知道；信息不够时要自己决定去看更多 |
| ⑥ 引用核验       | 程序                 | 挡幻觉靠程序，不靠 prompt                                      |
| ⑦ 理由站不站得住 | **审查 agent** | 要理解语意，字符串比对做不到                                     |
| ⑧ 组结果         | 模板                 | 只是组装                                                       |

### 拓扑

| 层      | 拓扑                          | 为什么                                                 |
| ------- | ----------------------------- | ------------------------------------------------------ |
| ④→⑤  | parallelization（sectioning） | 分几群由数据决定，每群各自判断、互不干扰，平行跑比较快 |
| ⑤⇄⑦  | evaluator-optimizer           | 一个产出、一个打分，不合格打回重做                     |
| ⑤ 内部 | agent＋tool                   | 判断 agent 自己决定要不要调用 get_person_timeline      |

### 保险

| 风险         | 做法                                                                                                                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 死循环       | 每个判断 agent 最多调用 4 次 tool；审查最多打回 2 轮                                                                                         |
| 输出格式坏掉 | agent 输出用 pydantic 验，不合格重来一次                                                                                                     |
| 超时或出错   | 整个 agent 层超过时限（45 秒，`.env` `AGENT_TIMEOUT`）或出错 → **退路**：跳过 ④–⑦，没判断完的群直接显示 ③ rerank 的结果（原设计的「一次 LLM 补说明」07 #5 还没接） |
| 读者干等     | 每一步完成就推到检索过程面板（SSE），读者看得到 agent 在做什么                                                                               |

### 分工

| 谁           | 做什么                                                                                    |
| ------------ | ----------------------------------------------------------------------------------------- |
| 同学（RAG/） | ② 召回、③ rerank、⑥ 引用核验、增量索引，包成函数给 agent 层 import 调用                |
| Ken          | ① 处境抽取（用 07 #2）、④ 分群与统计、⑤ 判断 agent、⑦ 审查 agent、⑧ 模板、推荐理由红绿灯、get_person_timeline、退路、SSE 推播 |

### ❓ 待定（延到决赛）

- **分群规则**：成绩差多少算同一群、人太少的群要不要并掉
- 「X 失败怎么办」把「失败」当结果硬筛，搜到太少

## 四、流程 C：脱机评估

```
30 题测试集（含 5–8 题对抗题）
   ├ 跑流程 B（multi-agent） → Hit@5、MRR、对抗题通过率
   ├ 对照组 1：只跑 ①–③（rerank 前 5 人）→ 比较 agent 有没有让结果变好
   └ 对照组 2：全部文章直接丢给 DeepSeek → 比较准确率、延迟、token 成本
```

## 五、流程 D：经验保鲜度核验（2026/10/21 从未来展望拉回，只做光华）

这版只做一个学院（光华），机制完整。程序在 `backend/app/freshness.py`，提示词 07 #8–#10。

```
爬虫（`python -m app.freshness crawl`；设计是每天 cron）：光华金融硕士、学术硕博的「招生简章」列表页 → 标题有「夏令营」＋年份的新网址才抓
   → 通知是嵌的 PDF，pypdf 取文本 → notices 表
   → 07 #9 抽规则（8 种规则类型）→ rules 表；引用对不上原文的丢掉，同类型多条合并
   → 重判这个项目底下的主张

文章入库（发文／改文背景跑、import_samples）
   → 程序先筛：正文含「光华」才做
   → 07 #8 抽客观主张（原句逐字核对）→ claims 表
   → 程序按 (项目, 规则类型) 挂到最新一年的规则，不叫 LLM

判断（07 #10）：一条规则一次判断底下所有主张 → valid／changed／unknown；引用不在通知原文里 → unknown
读的时候：valid 但依据的通知早于今年 → 🟡 待更新（今年通知还没出）
文章页：句子标色＋下方一行依据（官方原文、通知年份、通知链接）
```

| | 程序 | LLM |
|---|---|---|
| 抓列表、比对新网址、PDF 取文本 | ✅ | |
| 通知 → 规则 | | 07 #9 |
| 文章 → 主张 | 先筛「光华」 | 07 #8 |
| 主张挂规则 | 按 key 比对 | |
| 判断 | 引用核验、🟡 按年份算 | 07 #10 |

核验次数跟**规则数**成正比，不跟文章数：一份新通知只重判它影响的规则，挂在下面的句子一起变色。

10/21 深夜已上线：crawl 6 份通知、45 条规则；光华 150 篇示例导入后抽出 205 句招生规则主张。

10/21 本机实测：爬到专硕 2024–2026、学术 2024–2026 共 6 份通知；一篇照 2024 年规则写的测试文抽出 4 句，「分三批」「第三批可交前 6 学期成绩单」「学术营英语证明如有才交」判已变更，「专硕营学术营不能兼报」判仍成立，引用都逐字对得上 2026 通知。
